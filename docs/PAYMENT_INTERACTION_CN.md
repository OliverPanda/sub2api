# 中转站充值交互对齐与 Bridge 落地

## 1. 结论

XDD API 的充值入口已经按成熟中转站的主流程落地：

```text
账户与余额
  -> 选择固定充值档位和数量
  -> 创建订单（档位与支付渠道解耦）
  -> 展示该档位实际允许的全部支付方式
  -> 打开支付链接或扫描二维码
  -> 页面自动轮询到账状态
  -> 充值历史可搜索、筛选、展开详情
  -> 未完成订单可继续支付
```

Bridge 是充值体验层，Dujiao-Next 是支付与订单层，Sub2API 是账号与余额层。浏览器只展示服务端返回的状态，不参与价格计算、支付真伪判断或余额入账。

## 3. 当前用户流程

```text
已登录 Sub2API
  -> 打开 /shop/
  -> 从同源 localStorage.auth_token 读取登录态
  -> 调用 /api/catalog 获取账号、余额、SKU 和客服配置
  -> 选择 SKU 和数量，不选择支付渠道
  -> POST /api/orders 创建 Bridge 订单与 Dujiao 订单
  -> GET /api/payment-channels?order_no=... 获取该订单允许的全部渠道
  -> POST /api/orders/{orderNo}/pay 生成支付单
  -> 展示 pay_url 或 qr_code
  -> 每 3 秒调用 /api/orders/{orderNo}/refresh
  -> Bridge 向 Dujiao 查单并核对金额
  -> 支付确认后通过 Sub2API Admin API 幂等入账
  -> 到账后刷新账户余额并停止高频轮询
```

安全约束：

- JWT 不进入 URL、页面日志或第三方跳转参数。
- 支付方式来自 Dujiao 实际启用的通道，前端不能伪造。
- 订单金额和到账额度由服务端 SKU 计算。
- 回调只作为“可能有支付变化”的通知，不是到账依据。
- Bridge 必须重新查单，核对订单 ID、币种和实付金额后再入账。
- 同一 Bridge 订单使用固定兑换码和幂等键，重复回调不能重复增加余额。

## 4. 本次已实现的交互

### 4.1 充值历史搜索

充值记录支持输入 Bridge 充值单号进行即时过滤，便于用户把客服提供的信息与页面订单对应起来。

### 4.2 状态筛选

页面提供以下筛选：

| 筛选项 | 包含状态 |
| --- | --- |
| 待支付 | `created`、`pending_payment` |
| 处理中 | `paid`、`crediting`、`credit_failed` |
| 已到账 | `credited` |
| 已关闭 | `canceled`、`refunded` |

页面显示“当前结果 / 全部记录”的数量，空结果和全部为空使用不同提示。

### 4.3 订单详情

可展开查看：

- 充值单号
- 套餐和数量
- 应付金额和到账额度
- 创建时间
- 支付确认时间
- 到账时间

时间字段由服务端返回，前端只做本地化显示。

### 4.4 继续支付

用户关闭支付页后，不需要重新创建订单：

1. 在充值历史中找到“待支付”订单。
2. 点击“继续支付”。
3. 前端先重新读取服务端订单。
4. 如果订单已有支付链接或二维码，直接复用。
5. 如果没有支付页，则按当前档位重新获取全部允许渠道；只有一个渠道时自动生成支付单，多个渠道时展示收银台选项。
6. 支付页重新打开后继续自动轮询。

支付链接和二维码只在 `created` / `pending_payment` 状态显示。已到账、已关闭或已退款订单不会展示可支付入口。

### 4.5 状态与异常提示

| 状态 | 页面提示 | 用户动作 |
| --- | --- | --- |
| `created` | 待提交 | 等待支付页生成或重试 |
| `pending_payment` | 等待支付 | 扫码、打开支付页或继续支付 |
| `paid` | 支付已确认，正在到账 | 等待自动刷新 |
| `crediting` | 正在到账 | 等待，不要重复下单 |
| `credited` | 充值成功 | 返回控制台或继续充值 |
| `credit_failed` | 到账重试中 | 立即查询；持续失败联系客服 |
| `canceled` | 已取消 | 如已付款联系管理员 |
| `refunded` | 已退款 | 联系管理员核对余额 |

`credit_failed` 表示支付已被确认，但 Sub2API 入账失败。系统会自动重试，不会要求用户再次付款。

### 4.6 档位通用与支付方式选择

SKU 只描述金额和到账额度，不保存、绑定或提交 `channel_id`。用户选完档位后，Bridge 才创建 Dujiao 订单，并按该订单查询实际允许的全部支付渠道。这样同一个档位在所有已启用且允许该商品的支付渠道上通用。

当前 Dujiao Channel API 创建支付单时必须指定一个具体渠道，且没有返回“统一托管收银台”的接口。因此：

- 只有一个可用渠道时，Bridge 自动生成支付单，用户无需再选。
- 有多个可用渠道时，必须由用户选择微信、支付宝等具体付款方式；这是支付方式选择，不是档位绑定渠道。
- 不会随机或默认选择一个渠道来冒充“全渠道通用”，否则用户可能只看到单一付款方式，且容易出现重复支付和订单竞态。

如果要做到多个渠道下也完全不选择支付方式，需要上游提供统一收银台接口，或接入一个真正支持微信/支付宝聚合收银台的单一支付 Provider。

## 5. 暂不加入的交互及原因

- **自定义金额**：当前 SKU 固定，便于设定到账额度、对账和风控。后续若开放，必须由服务端同时返回应付金额和到账额度。
- **前端直接发起支付**：会暴露密钥，也无法可靠验签，必须由 Bridge 服务端调用 Dujiao。
- **支付成功即加余额**：前端结果可伪造，只能以 Dujiao 查单和 Sub2API 幂等入账为准。
- **未经验证的取消按钮**：如果 Dujiao 已创建支付单，取消与支付回调可能发生竞态。先确认供应商取消接口、支付中状态和退款规则，再开放。
- **未经验证的退款按钮**：退款涉及支付渠道原路退回、余额回收和已消费额度，不能只改订单状态。
- **同时开放两套充值入口**：Sub2API 原生充值和 Bridge 不能同时作为正式入口，否则容易重复入账和口径分裂。
- **自动接受新价格**：Dujiao 商品价格变化时返回 `PRICE_CHANGED`，必须由运营刷新配置，不能静默按新价格扣款。

## 6. 运营与异常处理

### 支付成功但余额未到账

1. 查 Bridge 订单的 `credit_failed` 状态和 `last_error`。
2. 查 Dujiao 订单是否确实已支付，核对金额和币种。
3. 检查 Sub2API Admin API Key、网络和接口权限。
4. 修复后调用管理重试接口。
5. 核对 Sub2API 兑换码或余额流水，确认只入账一次。

### 用户说付款了但订单仍是待支付

1. 让用户提供充值单号，不要只按金额搜索。
2. 在 Bridge 管理接口和 Dujiao 后台查支付流水。
3. 执行服务端查单，不要手工改数据库。
4. 确认已支付后让自动入账或管理重试完成。

### Dujiao 已退款或部分退款

当前 Bridge 会把 `refunded` / `partially_refunded` 映射为已退款并停止自动入账。已经入账的余额如何回收需要人工核对，不能由前端直接扣减。

## 8. 上线原则

1. `/shop/` 是唯一正式自助充值入口。
2. 上线前必须完成一笔低金额真实订单闭环。
3. 支付异常先保留订单和错误，再修复入账能力，不要删除已支付记录。
4. 对账至少覆盖 Dujiao 支付流水、Bridge 订单、Sub2API 余额流水。
5. 任何新增支付渠道先确认回调签名、查单接口、退款能力和结算币种，再开放给用户。
