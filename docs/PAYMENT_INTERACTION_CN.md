# 中转站充值交互对齐说明

## 1. 对齐目标

参考 Done-Hub 等成熟中转站的充值交互，XDD API 的充值页应做到：

1. 用户不用重新登录，打开充值页即可看到当前账号和余额。
2. 先看见固定充值档位，再选择支付方式。
3. 付款后页面自动轮询，不要求用户自己判断是否到账。
4. 支付成功、到账失败、取消、退款都有明确状态和下一步动作。
5. 充值记录可追溯，支付和客服入口在异常时可见。
6. 服务端对价格、支付状态和幂等负责，前端只展示结果。

## 2. 当前实现的用户流程

```text
已登录 Sub2API
  -> 打开 /shop/
  -> 读取同源 localStorage.auth_token
  -> 调用 /api/catalog 获取用户和充值档位
  -> 选择金额和数量
  -> 调用 /api/payment-channels 获取可用支付方式
  -> 选择支付方式并点击“立即充值”
  -> Bridge 创建 Dujiao 订单和支付单
  -> 显示支付链接或二维码
  -> 页面每 3 秒查询一次订单状态
  -> paid / crediting / credited / credit_failed 状态可见
  -> 到账后提示返回 XDD API 控制台
```

订单列表会展示最近 30 条充值记录。页面不会把 JWT 放进 URL，也不会要求用户再次输入 Sub2API 密码。

## 3. 与 Done-Hub 交互的对应关系

| 交互能力 | Done-Hub 参考做法 | 当前 XDD Bridge | 说明 |
| --- | --- | --- | --- |
| 固定充值档位 | TopupCard 展示套餐 | 已实现 | 服务端 SKU 配置 |
| 数量选择 | 套餐数量或固定金额 | 已实现 | 有最小/最大数量 |
| 支付方式选择 | PayDialog 选择渠道 | 已实现 | 从 Dujiao 支付通道动态读取 |
| 跳转支付 | 新窗口/当前页跳转 | 已实现 | `pay_url` |
| 扫码支付 | 展示二维码 | 已实现 | `qr_code` 支持 data URL 或 HTTPS URL |
| 订单轮询 | 前端定时查询 | 已实现 | 每 3 秒，页面隐藏时暂停实际请求 |
| 支付成功提示 | 显示成功并刷新余额 | 已实现 | 重新加载 catalog |
| 失败重试 | 提示联系管理员/重试 | 已实现 | `credit_failed` 自动重试，也支持管理接口重试 |
| 充值记录 | 订单表格 | 已实现 | `/api/orders` 最近 30 条 |
| 客服入口 | 异常订单显示客服 | 已实现 | 由 `BRIDGE_SUPPORT_URL` 控制 |
| 自定义金额 | 部分站点支持 | 未启用 | 固定 SKU 更便于对账和风控 |
| 支付图标 | 渠道 logo | 未实现 | 仅为视觉增强，不影响支付 |
| 未完成订单继续支付 | 订单列表再次发起支付 | 部分支持 | 可调用 `/pay`，但前端尚未做专门按钮 |

## 4. 界面状态设计

| 状态 | 文案建议 | 用户动作 |
| --- | --- | --- |
| `created` | 待提交 | 等待支付单创建 |
| `pending_payment` | 等待支付 | 扫码或打开支付页面 |
| `paid` | 支付已确认，正在到账 | 等待自动刷新 |
| `crediting` | 正在到账 | 等待，不要重复下单 |
| `credited` | 充值成功 | 返回控制台或继续充值 |
| `credit_failed` | 到账重试中 | 可立即查询；持续失败联系管理员 |
| `canceled` | 已取消 | 如已付款联系管理员 |
| `refunded` | 已退款 | 联系管理员核对余额 |

关键体验约束：

- 支付成功后停止高频轮询，避免无意义请求。
- 同一支付按钮在请求期间禁用，防止重复创建订单。
- 创建订单使用 `Idempotency-Key`，重复点击不能产生多笔订单。
- 页面刷新后从订单记录继续查看状态。
- 任何“余额已到账”提示都必须来自服务端 `credited` 状态，不能由前端支付跳转结果推断。
- 移动端优先保证二维码、支付链接和返回控制台按钮可操作。

## 5. 支付渠道展示

Bridge 不硬编码“支付宝/微信”名称，而是展示 Dujiao 后台当前启用的支付通道。这样：

- 支付渠道上下线不需要改前端代码。
- 同一套页面可接支付宝、微信、Stripe、卡密或其他 Dujiao 适配器。
- 渠道审核未通过时不会显示一个实际不可用的按钮。
- 后端仍应在创建支付单时校验渠道 ID，不能只依赖前端展示。

建议运营侧统一渠道名称，例如：

```text
支付宝
微信支付
银行卡 / Stripe
```

不要使用容易让人误解为官方直连的名称，除非商户资质和通道确实是官方直连。

## 6. 异常交互

### 价格变化

Dujiao 商品价格被修改后，Bridge 返回 `PRICE_CHANGED`。前端应提示：

> 充值价格已更新，请联系管理员刷新配置后重试。

不要自动按新价格扣款，否则用户看到的金额和实际支付金额可能不一致。

### 支付成功但入账失败

订单状态为 `credit_failed`，页面提示系统自动重试。管理员处理顺序：

1. 查 Bridge 订单的 `last_error`。
2. 查 Dujiao 订单是否确实已支付。
3. 检查 Sub2API Admin API Key 和接口连通性。
4. 修复后调用管理重试接口。
5. 核对 Sub2API 兑换码/余额流水，确认只入账一次。

### 用户关闭支付页

用户重新打开 `/shop/`，从充值记录找到订单并点击查询。Bridge 仍会通过 Dujiao 查单；不要求用户回到原来的支付页面。

## 7. 不建议现在加入的交互

- **自由输入金额**：增加对账、退款、风控和汇率复杂度；当前固定 SKU 足够。
- **前端直接调用支付平台**：会泄露商户密钥，也无法可靠验签。
- **支付成功后前端直接加余额**：可伪造，必须禁止。
- **同时显示两套充值系统**：容易重复入账和口径不一致。
- **自动按 Dujiao 新价格下单**：用户确认前不应改变应付金额。

## 8. 验收清单

```text
[ ] 未登录访问 /shop/ 不泄露用户信息
[ ] 登录后显示邮箱和当前余额
[ ] 无 SKU 时有清晰提示
[ ] 支付方式来自 Dujiao 实际可用通道
[ ] 重复点击充值不会创建重复订单
[ ] 支付页可打开，二维码可显示
[ ] 支付成功后 3 秒内能看到状态变化
[ ] 到账失败有重试中提示
[ ] 刷新页面后仍能看到订单历史
[ ] 移动端操作不遮挡按钮
[ ] 客服入口只在配置后显示
```
