# Sub2API 渠道运营策略

> 面向对象：平台管理员、上游渠道运营、值班人员
> 适用范围：渠道质量评估、渠道监控低分排查、账号与渠道调度优化、阈值治理、变更与回滚
> 更新时间：2026-10-26
> 线上生产阈值必须以实际页面和数据库配置为准；本文列出的代码默认值、迁移值和示例值不能替代线上核对。

## 1. 目标与基本原则

渠道运营的目标不是让监控页面全部变绿，而是在可控成本下持续提供：

1. **可用性**：请求能成功完成，不因账号、额度、网络或模型配置问题频繁失败。
2. **稳定性**：错误率、超时率、限流率和并发排队保持在可解释范围。
3. **响应速度**：首 Token 延迟、P95/P99 延迟不持续恶化。
4. **可恢复性**：上游异常时能快速降权、切换或暂停，修复后可安全恢复。
5. **可追溯性**：每次调整都有原因、范围、观察指标和回滚方式。

执行原则：

- **先看样本量，再看分数**：样本不足时不得直接判定渠道质量差。
- **先看错误构成，再看综合健康分**：相同分数可能对应完全不同的故障。
- **按平台、分组、模型、上游账号逐层定位**：不要因为一个红色色块关闭整个渠道。
- **每次只改一层**：账号、渠道路由、模型映射、代理和阈值不要同时修改。
- **不以调低阈值代替修复问题**：阈值用于治理，不是故障修复工具。
- **不以提高并发硬扛上游限流**：用户并发、账号并发和上游容量必须分别评估。
- **保留证据后处置**：日志、请求 ID、错误类别和时间窗口应可关联，但不得记录或公开真实密钥、Token、Cookie 和用户隐私数据。

## 2. 先区分两类“渠道监控”

Sub2API 中有两套不同语义的监控，不能混用。

| 项目 | 主动探测监控 | V2 真实流量健康监控 |
| --- | --- | --- |
| 常见入口 | `/admin/channels/monitor` | `/monitor` |
| 数据来源 | 定时向上游发起探测请求 | 聚合用户真实请求的用量日志和错误日志 |
| 主要回答 | 上游现在能不能通、主模型是否可用 | 用户实际使用是否稳定、慢在哪里、错在哪里 |
| 核心指标 | 当前状态、7 天可用率、请求延迟、主/附加模型状态 | 成功率、错误率、TTFT、缓存率、综合健康分、错误分类 |
| 适合排查 | 凭据失效、模型下线、网络不通、响应为空 | 间歇性失败、限流、流式中断、慢请求、特定分组质量问题 |
| 不应直接用于 | 判断全部真实用户体验 | 单次探测式验收 |

主动探测保持既定的 **120 秒周期及 jitter**。不要为了临时排查把探测频率调高；更高频率会增加上游压力，也可能制造限流和误报。最终周期以线上配置为准。

### 2.1 主动探测状态语义

| 状态 | 含义 | 运营解释 |
| --- | --- | --- |
| `operational` | 探测成功且未超过慢请求阈值 | 当前基本可用 |
| `degraded` | 请求成功，但耗时超过 6 秒，或额度类检查触发降级 | 可用但变慢或容量接近边界，需要持续观察 |
| `failed` / `error` | 探测失败、凭据错误、网络错误、响应为空等 | 需要按错误类型处置 |
| 单次探测超时 | 单次探测总超时为 45 秒 | 超时不必然代表整个渠道永久不可用，应结合趋势判断 |

### 2.2 主动探测结果处置

| 探测结果 | 常见原因 | 优先处理 |
| --- | --- | --- |
| `401` / `403` | API Key、OAuth Token、授权状态、账号白名单、出口 IP 或自定义 Header 错误 | 更新凭据、重新授权、检查 Header 与出口 IP；不要在未核实前关闭渠道 |
| `404` / `model not found` | 模型名错误、上游未开放该模型、模型映射错误 | 对照上游实际模型清单修正映射 |
| `400 invalid request` | OpenAI/Anthropic/Gemini 协议模式错误、请求体覆盖错误、参数不兼容 | 检查 API Mode、Body Override 和探测请求体 |
| 连接失败、TLS、DNS、超时 | 本机出口网络、代理、DNS、上游限流或上游故障 | 对比直连与代理，检查 RTT、丢包、HTTP/2 和流式连接 |
| 成功但持续 `degraded` | 上游本身慢、地区链路差、代理绕路、账号限速 | 对比同模型其他账号和地区；必要时降权而不是直接删除 |
| 主模型失败但附加模型正常 | 主模型配置、权限或上游临时故障 | 优先更换稳定的主模型；附加模型正常可暂时兜底 |
| HTTP 2xx 但响应为空 | 上游返回空内容、协议不兼容或反代改写 | 抓取脱敏响应特征并检查协议转换，不可只按状态码判成功 |

### 2.3 运营排障的三层视图

| 层级 | 页面 | 能回答什么 |
| --- | --- | --- |
| 聚合健康监控 | `/monitor` | 哪个平台、分组、模型的成功率、错误率、TTFT、健康分变差 |
| 请求/上游错误明细 | `/admin/ops` | 具体哪个账号报错、HTTP 状态码、上游状态码、错误消息 |
| 账号状态/额度 | `/admin/accounts` | 账号是否被限流、临时停调、最近使用、测试、已配置限额 |

使用边界：

- `/monitor` 负责平台、分组和模型的趋势判断；V2 健康聚合不按单个上游账号统计，不能只在健康分页面定位到具体账号。
- `/admin/ops` 才能下钻到 `account_id`、HTTP 状态码、上游状态码和具体错误消息，适合确认故障归属与影响范围。
- `/admin/accounts` 负责账号调度状态、限流/临时停调、测试结果和限额配置。账号页顶部的“上游余额总览”只读取最近一次计费探测持久化的余额快照，点击刷新不会主动探测上游。
- 第三方网关没有标准余额接口，或探测结果不含 `balance` 字段时，页面应显示“未知”或 `-`；不能从健康分、成功率或累计用量猜测真实钱包余额。
- 上游余额总览位于管理员账号管理页，对应接口 `/api/v1/admin/accounts/upstream-balances` 属于管理员路由组；前端路由和后端接口都必须拒绝普通用户访问，不能只做页面隐藏。

## 3. V2 健康分与判定边界

### 3.1 综合健康分

在满足最小样本量时，V2 综合健康分由三部分组成：

```text
综合健康分 = 错误率得分 × 60% + 首 Token 延迟得分 × 20% + 缓存率得分 × 20%
```

当某一维度样本不足时，该维度不会参与本次加权；实际权重会按可用维度重新归一化。

| 综合分 | 健康等级 | 默认运营含义 |
| ---: | --- | --- |
| `80–100` | `healthy` | 健康，保持常规观察 |
| `50–79` | `warning` | 需关注，结合趋势和错误构成定位 |
| `0–49` | `critical` | 异常，应进入排查或降权流程 |
| 无分数 | `unknown` | 样本不足或关键数据缺失，不能直接判定渠道差 |

### 3.2 样本规则

- 代码工厂默认最小样本量为 **50**。
- 请求总数不足最小样本量时，整体健康状态为 `unknown`。
- TTFT 和缓存率还分别要求各自样本量达到最小样本数。
- 低流量渠道可能需要更长周期才能形成有效判断，应看 24 小时或 7 天，而不是用几分钟数据下结论。
- 大流量渠道也要防止短时突发污染判断，至少确认异常是否连续出现。

### 3.3 各维度状态

错误率采用“越低越好”：

- 低于 warning 阈值：健康。
- 达到 warning 阈值：需要关注。
- 达到 critical 阈值：严重异常。

TTFT 采用“越低越好”：

- 不高于目标值：满分。
- 达到 warning 阈值：变慢但可能仍可用。
- 达到 critical 阈值：明显影响体验。

缓存率采用“越高越好”：

- 高于或等于 warning 阈值：健康。
- 低于 warning 阈值：需要关注。
- 低于 critical 阈值：严重偏低。
- 当 warning 和 critical 都配置为 `0` 时，缓存只展示、不参与健康分惩罚。

### 3.4 阈值必须区分来源

常见来源至少包括：

1. **代码工厂默认值**；
2. **数据库迁移默认值**；
3. **线上后台人工配置值**；
4. **某个部署环境的历史遗留值**。

三者可能不同。例如代码注释和迁移注释中的 TTFT、缓存率默认值可能不一致，线上也可能已被人工调整。因此：

- 任何“当前阈值是多少”的结论，必须以线上设置页面或只读数据库查询为准。
- 文档中的数值只能作为排查起点。
- 调整前先记录原值，避免无法回滚。
- 不把某个环境的缓存阈值直接复制到其他环境。

### 3.5 健康分不是业务成功率

健康分用于运营诊断，但存在以下边界：

- 被加入 `ignored_error_categories` 的错误类别仍会出现在错误构成中，但不参与错误率和健康分计算。
- 代码工厂默认忽略若干客户端或配置类错误；线上是否使用该默认列表必须核对。
- 即使健康分很高，也可能存在少量认证、余额、模型映射或客户端错误。
- 即使健康分很低，也可能主要是上游限流、网络或缓存策略导致，而不是渠道完全不可用。

因此，运营看板必须同时查看：**样本量、错误率、错误分类、TTFT、缓存率、并发排队、账号状态**。

## 4. 低分渠道的标准排查流程

### 第一步：确认数据有效性

1. 选择 7 天窗口，先看整体趋势。
2. 确认请求数、TTFT 样本数和缓存样本数是否达到最小样本量。
3. 检查是否处于数据回填、监控刚启用或大促突发阶段。
4. 如果分数为 `unknown`，先积累数据，不要调整阈值。

### 第二步：逐层缩小范围

按以下维度依次拆分：

```text
平台 -> 分组 -> 模型 -> 上游账号 -> 具体请求/错误日志
```

重点寻找：

- 是单分组低分，还是该平台所有分组都低分；
- 是单模型异常，还是所有模型都异常；
- 是单账号异常，还是账号池普遍异常；
- 是否集中在某个地区、代理、入口协议或客户端版本；
- 是否集中在某个时间段，并与发布、限流或上游故障时间吻合。

### 第三步：查看错误构成

不要只看红色综合分，至少确认：

- 错误分类分布；
- 错误是否来自上游还是客户端；
- HTTP 状态码和上游状态码；
- 是否发生重试、切换账号或 fallback；
- 是否有请求 ID 可关联到完整调用链；
- 错误是否已经被配置为忽略项。

### 第四步：检查容量和调度

在 Ops 仪表盘或等效监控中检查：

- 账号已用并发 / 总并发；
- 调度等待队列长度；
- 限流账号数；
- 错误账号数；
- 账号切换率；
- 代理失败和出口网络情况；
- PostgreSQL/Redis 等待、连接池、CPU 和内存。

队列高但上游错误低，说明容量或调度不足；队列低但错误高，说明渠道质量或配置有问题。两者处置不同。

### 第五步：只做一项调整

根据错误分类选择一项主要动作，例如：

- 降低问题账号并发；
- 暂停问题账号调度；
- 调整渠道优先级或权重；
- 修复模型映射；
- 刷新凭据；
- 替换代理；
- 增加健康账号。

不要同时改变用户并发、账号并发、代理、分组和监控阈值，否则无法判断哪项调整有效。

### 第六步：在明确窗口内观察

| 观察阶段 | 建议窗口 | 目的 |
| --- | --- | --- |
| 即时验证 | 5–15 分钟 | 确认配置已生效、错误是否停止扩大 |
| 短期观察 | 30–60 分钟 | 确认没有引发新的限流、排队或账号切换 |
| 日内观察 | 24 小时 | 对比错误率、TTFT、成功率和队列趋势 |
| 周期复核 | 7 天 | 判断是否真正改善，还是只是短时波动 |

若指标恶化或影响扩大，立即回滚，不要在故障中继续叠加修改。

## 5. 按错误类别的处置手册

| 错误类别 | 典型表现 | 优先原因 | 推荐动作 | 不要做什么 |
| --- | --- | --- | --- | --- |
| `rate_or_capacity` | `429`、`529`、overloaded、concurrency limit、capacity | 上游限流、账号并发过高、健康账号不足 | 降低问题账号并发；增加健康账号；检查队列、限流账号数和错误账号数；必要时对问题渠道降权 | 不要通过提高用户并发解决；不要无限重试 |
| `timeout` | `408`、`504`、deadline exceeded、gateway timeout | 代理绕路、DNS、RTT、丢包、上游慢、流式连接异常 | 对比直连和代理；检查出口 IP、地区、HTTP/2、流式超时；只对该渠道或模型修复 | 不要因单模型超时修改全局网络 |
| `transport_or_stream` | connection reset/refused、TLS、HTTP/2、unexpected EOF、缺少终止事件 | 链路不稳定、代理异常、协议兼容问题 | 区分短连接与流式请求；检查代理、TLS、HTTP/2 和 WS；必要时减少该上游权重 | 不要把流式中断仅当作 JSON 解析错误 |
| `upstream_5xx` | 上游 `500/502/503` | 上游故障、账号被限、渠道容量不足 | 降低权重、暂停问题账号、启用健康 fallback；持续观察上游恢复 | 不要用提高并发硬扛 |
| `upstream_forbidden` | 上游 `403` | IP 风控、账号限制、授权策略、代理出口异常 | 检查账号状态和出口 IP；更换出口或账号；必要时暂停调度 | 不要只改本地请求头掩盖问题 |
| `authentication` | `401`、Invalid API Key、OAuth 失效 | Key/Token 过期、授权被撤销、多实例刷新冲突、Header 错误 | 更新凭据、重新授权、检查自定义 Header；确认多实例时钟与 Token 刷新 | 不要绕过鉴权或在日志中暴露凭据 |
| `quota_or_balance` | insufficient quota/balance、credits、billing limit | 余额不足、套餐到期、额度耗尽 | 充值、续费、替换账号；检查余额告警阈值 | 不要把余额问题标记为客户端错误 |
| `account_pool_unavailable` | no available accounts、no healthy account、failover exhausted | 该模型无可用账号、分组限制、账号池全部异常 | 检查分组模型权限、账号状态、渠道限制和 fallback；补充健康账号 | 不要通过放宽监控忽略账号池为空 |
| `model_unsupported` | unsupported model、模型不存在 | 模型名错误、上游未开放、映射缺失 | 核对上游模型清单和本地模型映射；更新分组允许模型 | 不要反复切换协议测试同一错误 |
| `group_access` | group not allowed、group access | 用户分组、渠道分组或模型权限不一致 | 检查分组绑定、渠道可见范围和用户权限 | 不要直接开放所有分组 |
| `not_found` | `404` | URL、模型、部署路径或上游路由错误 | 核对 Base URL、API 路径和模型名 | 不要把 404 统一归类为网络故障 |
| `invalid_request` | `400`、deserialize、missing parameter、tool_choice | 客户端协议、请求体兼容、模型能力不匹配 | 对比最小请求；检查 API Mode、Body Override、工具调用和模型能力 | 不要为了变绿忽略所有 4xx |
| `context_limit` | context window、too many tokens | 上下文超过模型上限、历史裁剪失效 | 检查上下文长度、压缩和客户端重试策略；明确模型限制 | 不要用无限重试放大上游压力 |
| `content_policy` | safety policy、moderation、blocked keyword | 内容触发上游安全策略 | 向用户解释限制；记录类别但不要记录敏感正文 | 不要尝试绕过上游安全策略 |
| `client_cancelled` | `499`、context canceled | 客户端中断、超时后主动断开 | 分析客户端超时设置和网络；确认不是服务端先断开 | 不要计入上游渠道故障而误降权 |
| `internal` | Sub2API 自身 `5xx` | 应用异常、数据库/Redis、连接池、代码问题 | 检查应用日志、迁移、数据库、Redis 和最近发布；必要时回滚 | 不要先调整上游渠道 |
| `other` | 无法归类 | 新错误、日志信息不足、分类规则未覆盖 | 保留脱敏样本和请求 ID；补充分类规则或提交问题；先小范围观察 | 不要直接忽略 `other` |

## 6. 渠道、账号和分组优化策略

### 6.1 上游账号

- **认证失败或额度耗尽**：先修复或替换账号，不要只降低权重长期保留。
- **持续 429/529**：降低该账号并发，增加健康账号；若账号池仍然排队，再评估整体容量。
- **偶发超时**：先按地区和代理对比，确认是否为单账号链路问题。
- **高错误率账号**：降低调度优先级或暂停，保留一段时间观察；恢复前重新验证主模型和附加模型。
- **账号质量分级**：以 24 小时和 7 天错误率、TTFT、限流比例为证据，不用单次失败做永久决策。
- **用户并发统一为 20**：这是当前用户侧约束，不作为修复上游渠道低分的手段；只有在容量压测和商业策略确认后才调整。

### 6.2 渠道

- 一个渠道低分时，先确认是否集中在单一模型、单个账号或单一代理出口。
- 渠道整体健康和单账号健康要分别管理；不要把单个坏账号等同于整个上游不可用。
- 对持续异常但仍有部分可用能力的渠道，优先降权、限制模型或暂停问题账号，而不是立即删除。
- 删除渠道前必须确认没有用户仍依赖该分组，也没有破坏 fallback 和模型映射。
- 新渠道或修复后的渠道先小流量验证，再逐步增加权重。

### 6.3 分组

- 检查分组与渠道、模型、用户套餐和倍率是否一致。
- 低分如果只出现在某个分组，优先检查该分组的模型集合、账号池和渠道限制。
- 不要为一个分组的客户端错误放宽全局监控阈值。
- 对高质量付费分组，应保持更严格的可用性和 TTFT 目标；对测试分组可单独治理，但不混用结论。

### 6.4 模型映射

- 模型不存在、模型不支持或请求 404 时，先核对模型映射与上游实际能力。
- 模型 fallback 必须保持协议兼容和上下文语义兼容。
- 不要把一个要求严格工具调用或长上下文的请求无提示切换到能力较弱的模型。
- 出现上下文丢失、终止事件缺失或工具调用异常时，应同时检查上游兼容性和 fallback 链，不应只看健康分。

### 6.5 网络与代理

- 只在错误集中在特定地区、出口或渠道时调整代理。
- 调整前比较直连、当前代理和备用代理的 DNS、RTT、丢包、TLS、HTTP/2 和流式表现。
- 全局代理变更影响面大，必须作为受控变更执行，并保留回滚配置。
- 不把代理连接池耗尽误判成上游 429；要区分连接失败、排队和真实限流。

## 7. 监控阈值治理

### 7.1 调整阈值的前提

只有同时满足以下条件才考虑调整阈值：

1. 样本量足够，且异常已持续至少 24 小时；
2. 已确认错误主要不是渠道故障，而是统计口径或业务预期不匹配；
3. 已核对线上旧阈值和当前权重；
4. 调整有明确业务目标，例如缓存没有 SLA，不允许缓存率拉低健康分；
5. 已明确观察窗口和回滚值。

### 7.2 阈值调整原则

- **错误率**：不能为了让红色渠道变绿而提高 critical；应先修复 401、429、5xx 等问题。
- **TTFT**：应根据实际用户可接受体验和不同模型能力设定，不把所有 reasoning 模型按同一速度标准处理。
- **缓存率**：没有缓存 SLA 时可将 warning/critical 都设为 `0`，让缓存只展示不扣分；有 SLA 时用自身 7 天分布设阈值，例如 P25/P10，而不是抄其他环境。
- **最小样本量**：低流量渠道可适度增加观察窗口，但不能无限提高样本门槛来隐藏问题。
- **忽略错误类别**：只忽略已确认由客户端或明确业务策略导致的类别；认证、余额、上游 5xx、限流和超时不得为了变绿而默认忽略。
- **权重**：错误率、TTFT、缓存权重之和应保持 1.0，调整前先用历史数据回放评估。

### 7.3 阈值变更记录

每次阈值调整至少记录：

## 8. 变更、观察与回滚机制

### 8.1 变更分级

| 级别 | 示例 | 要求 |
| --- | --- | --- |
| 低风险 | 单账号暂停、单模型映射修复、单个测试分组调整 | 记录变更，30–60 分钟观察 |
| 中风险 | 渠道权重调整、多个账号并发调整、单平台阈值调整 | 双人复核或操作前备份，24 小时观察 |
| 高风险 | 全局代理、全局健康分阈值、数据库/Redis、发布升级 | 维护窗口、完整备份、明确回滚方案、持续值班 |

### 8.2 回滚触发条件

出现以下任一情况应立即回滚最近一次变更：

- 错误率或超时率继续上升；
- 并发等待队列持续增加；
- 429 扩大到一个以上分组；
- P95/P99 明显恶化；
- 新出现认证、余额、模型不可用等系统性错误；
- 用户投诉集中在变更后的时间窗口；
- 无法判断变更是否有效，且影响面正在扩大。

### 8.3 禁止事项

- 不因单个红色色块立即关闭整个渠道。
- 不为变绿而忽略全部错误类别。
- 不无脑提高用户并发或账号并发。
- 不同时修改代理、账号并发、渠道权重和阈值。
- 不把样本不足的 `unknown` 当成 `critical`。
- 不把缓存率低直接等同于渠道不可用。
- 不为了临时排查提高主动探测频率。
- 未确认问题归属前，不修改全局网络配置。
- 不在群聊、工单或文档中粘贴真实密钥、Token、Cookie、支付信息和用户隐私。

## 9. 日常运营节奏

### 每日

- 查看主动探测失败、连续 `degraded` 和可用率下降的渠道。
- 查看 `/monitor` 中 `critical` 渠道及其错误构成。
- 检查 429、超时、上游 5xx、认证失败和账号池不可用的异常变化。
- 检查并发队列、限流账号数、错误账号数和代理失败。
- 对新增异常建立时间线，避免只凭一张截图处置。

### 每周

- 按平台、分组和模型复盘 7 天错误率、TTFT 和缓存率。
- 比较不同上游渠道的稳定性和成本，识别长期低质量账号。
- 检查样本不足渠道，决定是继续观察、合并流量还是停止使用。
- 复核 `ignored_error_categories`，防止错误被长期“隐身”。

### 每月

- 复核健康分阈值、TTFT 目标和缓存策略是否仍符合用户预期。
- 清理长期无流量、无权限或已失效的渠道配置，但保留审计记录。
- 复盘重大故障：发现时间、定位时间、恢复时间、根因、改进项。
- 对高价值分组做容量演练和 fallback 验证。

